# Phase 23.1: Red Don Challenge capability boundary and playresult refactor - Context

**Gathered:** 2026-06-18
**Status:** Ready for planning

<domain>
## Phase Boundary

Phase 23.1 refactors the existing Red Don Challenge implementation before White catalog/runtime work resumes. It turns Don Challenge into the shared older-AC15 domain capability name, keeps the real `challengecompe.php` protocol surface separate, moves Red normal-play Don Challenge mutation into an explicit shared writer with era bindings, cleans up AdminApi projection, and centralizes the narrow Tokkun early-dispatch policy.

This phase may rename current `ChallengeCompe` domain/code/storage artifacts that are actually Don Challenge progress/reward behavior. It must preserve Red behavior and data while doing so. It must not implement White Don Challenge, invent new ChallengeCompe route semantics, add community/user-created challenge behavior, or introduce a broad generic AC15 playresult pipeline.

</domain>

<decisions>
## Implementation Decisions

### Don Challenge Naming Boundary
- **D-01:** Rename the shared application/domain capability from `ChallengeCompe` to `DonChallenge` where it represents monthly Don Challenge catalog, task, progress, reward, and AdminApi readback behavior.
- **D-02:** Preserve `ChallengeCompe` naming for real protocol route/wire surfaces such as `challengecompe.php`, `CommonChallengeCompeResponse`, and adapter-local wire DTOs. The Red `challengecompe.php` route remains compatibility/stub behavior unless new Red client evidence proves stateful route semantics.
- **D-03:** Red is the first Don Challenge binding, not the owner of the capability. White can add a binding later only after White-specific evidence proves data, field placement, readback, reward timing, and state semantics.

### Config And Schema Rename
- **D-04:** Perform a real, data-preserving schema rename from Red `ChallengeCompe` storage to Red `DonChallenge` storage. The migration must preserve existing progress and raw fact rows; dropping/recreating challenge data is not acceptable.
- **D-05:** Introduce DonChallenge-facing config/catalog names for the capability. Existing `EnableChallengeCompe` / `ActiveChallengeCompeBundleId` settings may remain as compatibility aliases during the transition, but new runtime code should speak Don Challenge when referring to the stateful capability.
- **D-06:** Keep table and entity ownership era-specific. The rename must not introduce shared gameplay persistence tables or repository-shaped adapters.

### Shared Writer And Playresult Ordering
- **D-07:** Move normal-play Don Challenge mutation into a shared `Ac15DonChallengeWriter` or equivalent service. The writer should own raw facts, progress upsert, distinct-song progress calculation, and reward grants through explicit era-supplied bindings.
- **D-08:** Red supplies the concrete catalog binding, Red `DbSet`s, Red save-data reward mutators, protocol limits, and play time. The shared writer must not hide `ITaikoDbContext` behind a broad repository layer.
- **D-09:** Preserve current playresult ordering: Tokkun is classified and handled before normal/Dani/Don Challenge writes; Don Challenge uses only valid normal-play stages; normal-play state and Dani behavior remain otherwise unchanged.

### AdminApi Projection
- **D-10:** Move mechanical Don Challenge task/reward DTO projection out of `GetDonChallengeQueryHandler` into Mapperly mappings or focused projection helpers. Handler logic should select era/capability data and call the projection, not hand-build every DTO field inline.
- **D-11:** AdminApi readback remains read-only. It must not opt users in, grant rewards, expose raw facts, or expose unsupported cabinet bucket names.

### Tokkun Dispatch Cleanup
- **D-12:** Centralize shared Tokkun classification and early-dispatch policy enough to remove duplicated Blue/Yellow/Red mode checks. Era-specific save-data access, recent-song table selection, and optional raw-history hooks stay in era files or era binding records.
- **D-13:** Do not create a full shared AC15 playresult pipeline in this phase. The cleanup is bounded to Tokkun detection/dispatch policy and preserving current no-cross-mode behavior.

### Folded Todos
- **Refactor Don Challenge capability boundary:** The pending todo `.planning/todos/pending/2026-06-17-refactor-don-challenge-capability-boundary.md` is folded into this phase. Its problem statement defines the source debt: Red works, but naming, writer ownership, config naming, AdminApi projection, and Tokkun dispatch shape would leak design debt into White if left as-is.

### the agent's Discretion
None. The user explicitly chose domain rename, data-preserving schema rename, shared writer, mapper/projection helpers, and shared Tokkun classifier.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `Ac15ChallengeCompeProgressEvaluator` already captures task/stage evaluation logic and can become Don Challenge evaluator code.
- `Ac15ChallengeCompeRewardDecisions` already computes reward grants and locked songs and can move under Don Challenge naming.
- `Ac15TokkunWriter` already centralizes tutorial/recent-song writes and can stay the write boundary while a smaller classifier/dispatch helper is added.
- Existing AdminApi Don Challenge contracts already use the desired user-facing name and can remain stable.

### Established Patterns
- Shared AC15 behavior belongs in `Application/Ac15/` only when behavior is value-identical and consumes explicit era profiles/tables/delegates.
- Persistence must remain direct and traceable through `ITaikoDbContext` and concrete era `DbSet`s, not through a broad repository abstraction.
- Controllers deserialize/map/call Mediator/map back. Business behavior belongs in Application handlers/services.
- Mapperly can be used for mechanical DTO projection, but generated source must be inspected for nontrivial mapper changes.
- Tests should protect observable persistence, readback, no-cross-era, and no-cross-mode behavior rather than source text or route inventory.

### Integration Points
- Red playresult mutation currently happens in `UpdatePlayResultCommand.Red.cs`; the shared writer should be called there with Red bindings.
- Red AdminApi readback currently uses `GetDonChallengeQueryHandler`; the handler should call projection helpers after reading capability data.
- Startup validation currently hardcodes Red ChallengeCompe settings; Phase 23.1 should introduce DonChallenge-facing validation without breaking existing config compatibility.
- EF migration work must rename Red challenge tables/data rather than recreating them.

</code_context>

- Preferred writer direction: `Ac15DonChallengeWriter` with era-owned table/save/catolog binding records.

- Keep `ChallengeCompe` names where they describe protocol route/wire DTOs or the stub compatibility endpoint.
