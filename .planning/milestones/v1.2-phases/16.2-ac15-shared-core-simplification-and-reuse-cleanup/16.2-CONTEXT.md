# Phase 16.2: AC15 Shared Core Simplification and Reuse Cleanup - Context

**Gathered:** 2026-06-10
**Status:** Ready for planning

<domain>
## Phase Boundary

Phase 16.2 is a broad AC15 Green/Blue/Yellow reuse cleanup phase after Phase 16.1's nullable-wire and Mapperly rewrite. It should simplify duplicated AC15 implementation code by moving matching behavior into canonical AC15 types, helpers, services, profiles, narrow row-shape interfaces, and direct EF shared services.

This phase does not add new Yellow runtime behavior, does not perform Phase 17 cabinet/RPCS3 smoke or final contract closeout, and does not merge era routes, generated wire DTOs, or EF tables. It refactors evidence-backed shared behavior while preserving era-owned persistence, era adapter routing, wire placement, and explicit special-mode branches.

</domain>

<decisions>
## Implementation Decisions

### Phase Scope And Sequencing
- **D-01:** Phase 16.2 covers the wider AC15 reuse surface from the user-referenced handoff, not only playresult cleanup.
- **D-02:** Sequence planning from low-risk to high-risk: canonical enums/helpers/DTO aliases first, then shop and Dani services, then normal-play adapter internals and playresult save-shell cleanup.
- **D-03:** Treat the earlier six-stage AC15 extraction plan as direction and context only. Current code already contains much of `Application/Ac15`, so downstream planning must audit current code before copying old plan steps.

### Canonical AC15 Types And Pure Helpers
- **D-04:** Replace matching duplicate Dan clear-grade enums with a canonical AC15 Dan clear-grade type when values and behavior match.
- **D-05:** Replace matching duplicate Blue/Green/Yellow shop item status enums with one canonical AC15 shop item status type where all current values are equivalent.
- **D-06:** Use canonical `Ac15CrownState` and `Ac15CrownService`; remove misleading Blue/Green crown state aliases where they no longer add behavior.
- **D-07:** Collapse `BlueDanHelpers`, `GreenDanHelpers`, and `YellowDanHelpers` into canonical AC15 Dan helper logic driven by `Ac15ProtocolLimits`.
- **D-08:** Reuse `Ac15ProtocolLimits` and `Ac15ProtocolBytes` for shared flag widths and bit helpers. Keep Blue battle and Green ghost constants era-local.
- **D-09:** Replace repeated Blue/Green/Yellow profile-counter helper logic with one AC15 counter updater behind typed save adapters.

### Dani Workflow
- **D-10:** Extract a shared AC15 Dani service for Dan validation, score and stage-score updates, packed Dan flags, `GotDanMax`, display-Dan normalization, and Dan costume application.
- **D-11:** The shared Dani workflow must use direct `ITaikoDbContext` access, concrete era `DbSet`s, narrow row-shape interfaces, and Mapperly projections. Blue, Green, and Yellow Dan EF entities and tables stay separate.

### Shop Reuse
- **D-12:** Share shop season behavior with explicit seed policy: Blue starts new shop season totals at zero; Green and Yellow seed first season totals from save data.
- **D-13:** Share item-shop purchase/status/unlock plumbing, but keep era-specific unlock policies. Green song purchases remain a no-op for release-song flags; Blue and Yellow song purchases set release-song flags.
- **D-14:** Shop cleanup must not introduce Banacoin wallet, payment, coupon, transaction, settlement, or receipt state.

### Normal Play And Playresult Cleanup
- **D-15:** Extract the duplicated AC15 playresult save shell: medal totals, tutorial flags, play time, area, profile counters, costume/unlock bits, and normal-save orchestration.
- **D-16:** Special-mode classification remains an era-local gate before the shared normal save shell. Blue battle, Blue Tokkun, Yellow Tokkun, and Green AI/ghost behavior are not generic AC15 behavior.
- **D-17:** Deterministic client behavior means there are no meaningful "invalid payload" contracts for AC15 playresult uploads. If the server cannot recognize a mode/shape, it should log the existing payload for replay, skip mutation, and return protocol success.
- **D-18:** Shapes still must be classified because normal, Dan, battle, Tokkun, AI/ghost, and unrecognized uploads require different handling.
- **D-19:** Factor repeated normal-play service internals where behavior is identical, including best/favorite/recent/crown-rank/user-exists/save helpers.
- **D-20:** Do not replace direct EF shared services with a broad reflection/string-based generic persistence adapter over all SongBest/SongPlay/Favorite/Recent tables.
- **D-20A:** The post-review persistence shape is a hybrid: use `ITaikoDbContext` and concrete era `DbSet`s directly, but add narrow Domain entity-shape interfaces for storage rows whose fields are genuinely identical across AC15 eras. Shared services should put duplicate algorithms behind generic helpers constrained by those row-shape interfaces, while Mapperly owns canonical record/entity projection overloads.
- **D-20B:** Do not add a custom source generator for per-era EF binding in this milestone. Mapperly is the only source-generation layer for this cleanup; if future eras make binding boilerplate painful, revisit generation after the generic entity-shape contracts stabilize.
- **D-20C:** Keep explicit era branches only at the binding/policy edge: selecting the concrete `DbSet`, applying real era behavior such as Green ghost sections or Green song-unlock no-op, using protocol limits, or preserving unsupported-mode boundaries. A branch whose only body difference is property-by-property update logic should be collapsed into a generic helper or Mapperly projection.

### Catalog And DTO Cleanup
- **D-21:** Prefer canonical `Application/Catalog/Ac15` value objects for item shop, telop, recommendation, Taikojuku, music info, and similar AC15 catalog shapes when behavior matches.
- **D-22:** Simple catalog-backed handlers such as folder, telop, recommend, and item-shop info can use shared AC15 helper logic that resolves the correct era profile and catalog snapshot.
- **D-23:** Move shared AC15 userdata and initial-data fields out of misleading Green/Blue/Yellow-named Common DTO partials into canonical AC15 DTO fields where the fields are genuinely shared. Era wire mappers still place data into adapter-local generated response DTOs.

### Hard Non-Reuse Boundaries
- **D-24:** Do not create shared AC15 EF tables or discriminator tables. `SongBest`, `SongPlay`, Dan, shop, favorite, recent, Tokkun, battle, and save tables stay era-owned.
- **D-25:** Do not create a shared generated AC15 wire assembly. Generated `Wire/` DTOs remain adapter-local.
- **D-26:** Do not infer routes or add success stubs because another AC15 era has a similar endpoint. Unsupported client features stay absent.
- **D-27:** Do not make Blue battle, Blue Tokkun, Yellow Tokkun, or Green AI battle generic AC15 modes.

### Verification Contract
- **D-28:** Verification is regression-slice driven. Use existing AC15, Green, Blue, and Yellow focused suites plus a temp-output Host build.
- **D-29:** Add or adjust tests only where a touched behavior is not already covered by observable behavior tests. Do not add source-shape assertions, implementation-string tests, or a new comprehensive reuse matrix merely to prove a refactor happened.

### the agent's Discretion
- Downstream agents may choose exact class names and file splits, such as `Ac15DaniService`, adapter helper records, or profile-specific policy objects, as long as the decisions above are preserved.
- Downstream planning may split the phase into multiple plans according to blast radius, but the sequence should remain low-risk canonical cleanup before heavier runtime workflow extraction.

</decisions>

## Existing Code Insights

### Reusable Assets
- `Application/Ac15` already contains `Ac15EraProfiles`, `Ac15ProtocolLimits`, `Ac15ProtocolBytes`, `Ac15CrownService`, `Ac15SelfBestService`, `Ac15TaikojukuService`, `Ac15CatalogReadbackService`, `Ac15InitialDataService`, `Ac15UserDataService`, `Ac15ItemShopService`, and `Ac15NormalPlayService`.
- Typed Blue/Green/Yellow adapters already exist for userdata, item shop, and normal play. Phase 16.2 should improve repeated internals rather than replacing them with a table-generic EF layer.
- Post-review correction removed repository-shaped Dani/item-shop/normal-play persistence adapters. Future work must not resurrect those classes; use direct `ITaikoDbContext`, narrow row-shape interfaces, generic helpers, and Mapperly projection overloads instead.
- The user-referenced handoff identifies concrete duplicate enum/helper/status/counter/DTO surfaces that remain after current AC15 core extraction work.

### Established Patterns
- Controllers deserialize wire DTOs, map to Common/Application DTOs, call Mediator, and map back to generated wire responses.
- Shared behavior belongs in `Application/Ac15`; route ownership, generated `Wire/` DTOs, and wire placement belong in era adapter projects.
- Persistence stays era-specific through `ITaikoDbContext` partial surfaces and concrete era `DbSet`s.
- EF remains the persistence/unit-of-work boundary. Entity-shape interfaces are allowed only as compile-time contracts for identical storage properties, not as repository, service, or behavior abstractions.
- Tests should verify observable handler/service/EF/API behavior, not source shape.

### Integration Points
- Planner should audit current implementations before copying any old stage-plan steps because Yellow and Phase 16.1 changed the current codebase after the original AC15 extraction design.
- The highest-risk integration surfaces are `UpdatePlayResultCommand.*`, Dan score/readback, shop state/purchase, and the direct EF normal-play service.
- Remaining Phase 16.2 plans must be amended to consume the hybrid row-shape decision before continuing from Plan 08; older plan text that references deleted Blue/Green/Yellow persistence or normal-play adapter classes is stale.
- Phase 17 depends on this phase. Do not move runtime smoke or final Yellow contract documentation into Phase 16.2.
