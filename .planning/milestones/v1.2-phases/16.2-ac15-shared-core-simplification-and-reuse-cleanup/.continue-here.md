# Continue Here - Phase 16.2 Post-Review Architecture Decision

The architecture blocker from the earlier Phase 16.2 execution has been discussed with the user and resolved into a concrete planning direction.

## Resolved Constraints

- No repository-shaped AC15 persistence layer. EF/`ITaikoDbContext` remains the persistence and unit-of-work boundary.
- No Blue/Green/Yellow adapter classes where the only difference is table/entity routing.
- Mapperly is mandatory for mechanical Application/Ac15 value/entity projection.
- Do not add a custom source generator for per-era EF binding in this milestone.
- Do use narrow Domain entity-shape interfaces for AC15 storage rows whose fields are genuinely identical across eras, plus generic EF helpers constrained by those interfaces.
- Keep explicit era branches only for binding/policy edges: concrete `DbSet` selection, Mapperly overload selection, protocol limits, Green ghost sections, Green song-unlock behavior, unsupported features, and special-mode gates.

## Decision

The user selected the hybrid architecture:

1. Add storage-shape interfaces such as `IAc15DanScoreDatum`, `IAc15DanStageScoreDatum`, `IAc15SongBestDatum`, `IAc15FavoriteSong`, `IAc15RecentSong`, and `IAc15ShopSeasonState`, following the existing `Domain/Entities/IAc15ShopItemState.cs` pattern.
2. Implement those interfaces on Blue/Green/Yellow entities where the row shape is identical.
3. Refactor `Application/Ac15` shared services to put duplicated algorithms behind generic helpers constrained by those interfaces.
4. Keep `ITaikoDbContext` and concrete era `DbSet`s directly visible from shared service code.
5. Keep Mapperly as the only source-generation layer.
