# Phase 16.1: AC15 Mapperly Mapper Rewrite and Presence Semantics - Context

**Gathered:** 2026-06-10
**Status:** Ready for planning

<domain>
## Phase Boundary

Phase 16.1 is a dedicated refactor phase for Green, Blue, and Yellow AC15 protocol mapping. It regenerates AC15 wire DTOs with nullable optional primitive support, removes production mapper dependence on protobuf `ShouldSerialize*` helper methods, and rewrites AC15 adapter mappers so mechanical wire/Common projection is generated by Mapperly instead of hidden inside hand-written methods annotated with `[Mapper]`.

This phase does not change client-visible route shapes, handler business rules, persistence ownership, or raw proto inputs except where repo-local protogen compatibility requires regeneration from immutable local proto evidence.

</domain>

<decisions>
## Implementation Decisions

### Wire DTO Presence
- **D-01:** Regenerate Green, Blue, and Yellow AC15 generated wire DTOs with repo-local protogen nullable optional primitive support, using `+nullablevaluetype=yes`.
- **D-02:** Treat `proto/` files as dumped protocol evidence. Do not edit proto inputs during this phase unless protogen compatibility forces a minimal, documented adjustment.
- **D-03:** Optional primitive presence at the adapter boundary must be represented by nullable generated C# properties wherever protogen supports it. Zero and absent must remain distinguishable without production mapper calls to `ShouldSerialize*`.
- **D-04:** Generated protobuf helper methods such as `ShouldSerializeTokkunTutorialFlg` are serializer internals, not application mapping API. They must not be called from production mapper code after the nullable wire regeneration.

### Mapperly Usage
- **D-05:** Green, Blue, and Yellow AC15 mappers must contain real Mapperly-generated mapping methods for mechanical projection. A class annotated with `[Mapper]` but only containing hand-written public mapping bodies is not acceptable.
- **D-06:** Manual mapper code remains allowed only for protocol/domain transforms that Mapperly cannot infer cleanly, such as classifiers, byte encoding, persisted optional-response emission, ordered raw-list preservation, and explicit response composition.
- **D-07:** Where a wrapper method must do manual orchestration, it should delegate the straightforward property copy and nested DTO projection to private or internal Mapperly partial methods.
- **D-08:** Remove or narrow era project-wide Mapperly warning suppressions that only existed to hide fake Mapperly usage. Any remaining suppression must be local and justified by an intentional manual transform.

### Scope And Compatibility
- **D-09:** Keep era adapter boundaries intact. Green, Blue, and Yellow keep their adapter-local `Wire/` folders, routes, controllers, and persistence ownership.
- **D-10:** Preserve direct-protobuf AC15 controller transport and existing Common DTO boundaries: controllers deserialize, map to Common DTOs, call Mediator, and map Common DTOs back to wire responses.
- **D-11:** Do not use source-text tests as the primary proof. Tests should verify generated type/property shape by reflection, protobuf serialization presence behavior, mapper behavior, handler no-cross-write behavior where relevant, and build output.

### the agent's Discretion
- The implementation can use focused reflection tests for nullable generated properties and Mapperly compile/build output because these are observable assembly contracts, not source-word scans.
- The implementation can split the refactor by mapper category if compile/test feedback shows specific mappers need local hand-written transforms.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- WwR08 and AdminApi show the intended Mapperly shape: `partial` mapper classes with bodiless mapping methods that source generation implements.
- Repo-local protogen exposes `+nullablevaluetype={yes|no}`, which is the correct fix for optional primitive presence rather than calling `ShouldSerialize*` inside mappers.
- Current AC15 Green/Blue/Yellow mappers contain hand-written mapping bodies even when annotated with `[Mapper]`, and production `ShouldSerialize*` calls are concentrated in item-shop and playresult mappers.

### Established Patterns
- AC15 adapters keep generated wire DTOs adapter-local and map through Common DTOs before Application handlers.
- Generated `Wire/` files are regenerated artifacts, not manually cleaned production source.
- Era state and routes remain separate even where Green, Blue, and Yellow behavior aligns.

### Integration Points
- Wire regeneration affects compile-time property nullability in mappers, controllers, and tests.
- Mapperly generation runs during normal build, so `dotnet build` is the primary architecture check.
- Tests should focus on reflection/serialization/mapper output rather than reading `.cs` files for strings.

</code_context>

<specifics>
## Specific Ideas

- The user explicitly identified the current AC15 mapper shape as a major anti-pattern because Mapperly has already been introduced.
- The user explicitly rejected inline cleanup and required a dedicated phase for the rewrite.
- The user explicitly rejected `ShouldSerialize*` in mappers because those helpers belong to protobuf internals.
- The user explicitly identified protogen nullable primitive support as the refactor point that should remove the presence issue.

</specifics>
