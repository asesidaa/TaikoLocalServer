# Phase 16.1: Patterns

## Use Existing Mapperly Shape

Existing real Mapperly usage follows this shape:

```csharp
[Mapper]
public static partial class SomeMapper
{
    public static partial Target Map(Source source);
}
```

For AC15 mappers that need orchestration, keep wrappers small:

```csharp
[Mapper]
public static partial class SomeMapper
{
    public static Target Map(Source source)
    {
        var target = MapCore(source);
        // Only protocol/domain transforms belong here.
        return target;
    }

    private static partial Target MapCore(Source source);
}
```

## Nullable Presence Pattern

- Optional primitive request fields should be nullable generated properties.
- Common DTO fields that need presence should remain nullable.
- Response mappers should set nullable generated response fields only when the Common DTO has a value.
- Do not call `ShouldSerialize*` from production mappers.

## Warning Pattern

- Remove global `NoWarn` entries that hide Mapperly diagnostics.
- If Mapperly cannot map a deliberate protocol transform, use mapper attributes or a targeted suppression with a comment in the smallest possible scope.

## Test Pattern

- Use reflection/serialization/mapper behavior tests.
- Avoid source-text assertions over `.cs`, `.csproj`, generator output text, or mapper bodies.
- Build is the source-generation proof.
