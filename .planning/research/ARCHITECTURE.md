# Architecture Research: White AC15 0.13 Support

## Summary
- White should be added as a first-class AC15 era with its own adapter project, generated wire DTOs, route prefix, catalog, persistence tables, Mapperly mappers, Host registration, AdminApi switches, and WebUI era metadata. It should not be modeled as a Red or Yellow variant.
- The existing Red and Yellow shape is the right template: unsuffixed Application dispatchers fan out to `.White.cs` partials, controllers stay thin, generated wire maps through `Application/Dtos/Common*`, and behavior lives in handlers/services.
- Reuse the shared AC15 services only where White has matching protocol fields and catalog data. White-specific `Ac15EraProfile`, limits, feature flags, and wire placement are the integration contract that prevents Blue/Yellow/Red assumptions from leaking in.
- White should start with normal AC15 surfaces that are visible in `proto/white/taiko.proto` and committed data under `ST7100-1`: BAID/profile, userdata, initial data, self-best, crowns, folders, telops, recommendations, Taikojuku, MyDon entry, playresult, reward/present support if field placement is proven, and Dani only if White payload/data evidence supports it.
- Missing features should remain absent. Do not add item shop, Banacoin wallet/payment, Tokkun, battle, gacha, or a standalone ChallengeCompe route unless White client/proto/log/IDA evidence proves those surfaces.
- Current White route/root evidence is incomplete. The local White IDB is zero bytes, so route prefix, startup/version route ownership, and any non-proto behavior need confirmation from cabinet/RPCS3 logs, a valid binary, or captures before they become hard contracts.

## Integration Shape
- **Domain:** Add `GameEra.White` and White-owned entities. Normal AC15 state should mirror Red/Yellow only at the interface boundary: `IAc15PlayProfileSaveData`, `IAc15CustomizationSaveData`, `IAc15SongUnlockSaveData`, `IAc15SongBestDatum`, `IAc15SongPlayDatum`, favorite/recent song rows, and Dani rows where White supports them. Do not share Red/Yellow tables.
- **Application AC15 profile:** Add `Ac15EraProfiles.White` with a White `Ac15FeatureSet`, `Ac15ProtocolLimits`, and `Ac15WirePlacement`. Treat existing common limits as a starting hypothesis only; verify byte widths, song counts, favorite/recent limits, Dan ranges, and section placement from generated White wire and observed payloads.
- **Application dispatchers:** Extend existing partial dispatchers with `.White.cs` implementations where the feature is present. Expected dispatch points include `BaidQuery`, `AddMyDonEntryCommand`, `UserDataQuery`, `GetInitialDataQuery`, `GetSelfBestQuery`, `GetCrownsDataQuery`, `GetFolderQuery`, `GetTelopQuery`, `GetRecommendQuery`, `GetTaikojukuQuery`, `UpdatePlayResultCommand`, and AdminApi read/write handlers. Keep unsupported White features returning unavailable/not implemented at the dispatch boundary rather than silently aliasing Red/Yellow behavior.
- **Application DTO flow:** Continue mapping White wire DTOs into `Common*` DTOs or AC15 envelopes before handlers. If White has fields that do not fit existing `Common*` shapes, add narrow White-aware common fields in Application instead of passing generated wire into handlers.
- **Infrastructure catalog:** Add `Infrastructure/GameDataCatalog/White` with `WhiteGameDataPaths`, `WhiteRequiredDataFiles`, `WhiteEraGameDataCatalog`, `IWhiteCatalog`, and catalog extension helpers. The data root should resolve through `PathHelper.GetDataPath(GameEra.White)` and the White config root should be `config/ST7100-1`. Required files should begin with `musicinfo.xml`, `musicmedleyinfo.xml`, `defmusic.bin`, and `fumen/tuning.bin`; consume `present.xml` and `spacialbaid.xml` only after parser/behavior ownership is defined.
- **Infrastructure persistence:** Add White DbSets and typed save extensions in `TaikoDbContext.White.cs`. Keep White normal score, crown, play datum, favorite, recent, Dani, reward/progress, and any challenge/present state in White-owned tables. Add no Tokkun, battle, shop, or ChallengeCompe tables until evidence requires them.
- **Game adapter:** Add `Adapters.GameProtocol.White` with generated `Wire/Game.cs` from `proto/white/taiko.proto` and generated `Wire/VsInterface.cs` from `proto/white/vsinterface.proto`. Controllers should follow Red/Yellow: deserialize direct protobuf, map through Mapperly, call Mediator, map back, and return protobuf. Do not manually edit generated `Wire/` files.
- **Route ownership:** White should have a White route prefix once proven, with shared startup/version routes only if client evidence matches the existing AC15 split. `proto/white/vsinterface.proto` contains startup/version messages, but that does not by itself prove the route prefix or whether White shares `/v01r00/chassis/*`.
- **Mapperly boundaries:** Mapper partials should stay source-generator driven. Handwritten code should be limited to conversion helpers discoverable by Mapperly, semantic section application methods, or narrow classifier helpers. Verify important mappings by building with `EmitCompilerGeneratedFiles=true` and inspecting emitted `Riok.Mapperly` `.g.cs` files, especially null handling, ignored members, and generated constants.
- **Host composition:** Add the White adapter project reference, `AddGameProtocolWhite`, disabled application-part removal, protobuf content-type fallback prefixes, Host config era key, validation cases, data copy/junction entries, and fatal error messaging. `ServerSettings:Eras:White` should be disabled until the minimum route/catalog surface is usable.
- **AdminApi/WebUI:** Extend existing era-routed AdminApi controllers and WebUI era helpers rather than adding White-only API shapes. Add White to `WebUiEra` supported/known eras and `IsAc15`. Keep Don Challenge navigation disabled for White unless a White-specific ChallengeCompe design exists.

## Shared AC15 Reuse Points
- `Ac15ProtocolBytes`: Reuse for bit/byte flag packing after White byte widths are verified. Do not assume Blue/Yellow/Red flag byte counts without generated-wire and payload checks.
- `Ac15UserDataService`: Reuse for building common userdata sections once White has a profile, snapshot adapter, and wire placement. White needs its own `WhiteAc15UserDataAdapter`.
- `Ac15InitialDataService`: Reuse for common initial data sections. Add White catalog snapshot support and omit item shop/gacha sections unless White evidence proves them.
- `Ac15CatalogSnapshotFactory`: Add `FromWhite`. This is the main catalog-to-common boundary for songs, medleys, folders, telops, recommendations, movies, customizations, unlock flags, and Taikojuku data.
- `Ac15CatalogReadbackService`, `Ac15SelfBestService`, and crown readback helpers: Reuse for White self-best/crown endpoints if White wire placement and limits match the common AC15 shape.
- `Ac15NormalStageFilter` and `Ac15NormalPlayWriter`: Reuse for normal playresult writes. White-specific mode classification must be supplied before writes; unsupported modes should not mutate normal score/crown/profile state.
- `Ac15CommonProfileMutation`: Reuse the Donpoint/reward path only if White playresult/userdata fields align with Red-style Donpoint semantics. Do not reuse Yellow medal or shop mutation paths.
- `Ac15DaniWriter` and Dani readback handlers: Reuse if White payloads and catalog data expose the same Dani contract. White Dan limits and safe fallback must come from the White profile.
- `Ac15MyDonEntryService`: Reuse with White typed save accessors and default save creation.
- `Ac15TaikojukuService`: Reuse if White has Taikojuku request/response messages and catalog file order. White needs its own sidecar or loader output for version-up data.
- `Ac15UserSettingsService`, `Ac15UserSettingsAccess`, and AdminApi user settings controllers: Reuse through White typed accessors. Add White partials; do not add a separate White settings API.
- `Ac15UnlockFlagAccess`: Add White accessors for title, costume, tone, and song flags. Keep title id `0` as the explicit empty/default title state.
- `Ac15ChallengeCompe*` services: Treat as late-stage optional reuse. White proto contains challenge-related fields, but there is no standalone ChallengeCompe route in the proto evidence. Require White-specific field placement, sidecar data, progress semantics, and readback proof before enabling.

## White-Owned Boundaries
- **Routes:** White route prefixes and startup/version aliases are White-owned evidence. Add controllers only for proven White endpoints; do not expose Red `/v08r01` or Yellow `/v09r02` aliases for White.
- **Wire DTOs:** White generated protobuf types live only under `Adapters.GameProtocol.White/Wire`. Do not reuse Red/Yellow generated DTOs and do not persist wire DTOs.
- **Mappers:** White mappers live in the White adapter and map generated wire to Application DTOs. Mapperly should generate projection bodies; handwritten mapper logic should stay as helper conversions/classification, not business behavior.
- **Persistence:** White gets separate EF entities, tables, migrations, and DbContext partials. Shared identity/card data can stay shared, but gameplay, unlock, reward, favorite, recent, Dani, and progress state must be White-owned.
- **Catalog:** White gets `IWhiteCatalog` and a White catalog implementation rooted at `Host/wwwroot/data/white/data` in source checkouts and `wwwroot/data/white/data` in published output. Runtime code should resolve paths through `PathHelper` and White path helpers.
- **Server-authored data:** White sidecars should be named explicitly, such as `white_event_folder_data.json`, `white_telop_data.json`, `white_recommend_songs.json`, `white_movie_data.json`, `white_taikojuku_verup_data.json`, `white_costume_data.json`, `white_title_data.json`, and `white_neiro_data.json`. Add intentionally empty sidecars when the runtime expects server-authored data but no entries are known.
- **Settings:** Add `ServerSettings:Eras:White`. Do not add White to shop-era validation. Add White challenge settings only if a White challenge feature is implemented and backed by White sidecar semantics.
- **Host packaging:** Host project data include/exclude rules, publish copy rules, and debug junction creation must include White paths. This is part of runtime behavior because published Host output must contain the same White server-authored JSON and data-root layout.
- **AdminApi/WebUI routing:** White should use `/api/{era}/...` routes and existing generic WebUI pages after controller switches are extended. Unsupported surfaces should be hidden or shown as unavailable, not wired to Red/Yellow responses.

## Build Order Recommendation
- **Phase 1: White foundation and route evidence.** Add `GameEra.White`, generated wire, adapter project skeleton, Host registration behind disabled config, content-type fallback, and no-state probe controllers only where route evidence is known. Confirm route prefix and startup/version ownership from logs, captures, or a valid White binary before locking the adapter surface.
- **Phase 2: Catalog and AC15 profile.** Add White data paths, required-file checks, catalog loaders, sidecars, `IWhiteCatalog`, DI registration, `Ac15CatalogSnapshotFactory.FromWhite`, and `Ac15EraProfiles.White`. Verify protocol limits and feature flags here before handler work depends on them.
- **Phase 3: Identity and readback MVP.** Implement White BAID/profile, MyDon entry, userdata, initial data, self-best, crowns, folders, telops, recommendations, Taikojuku, favorite/recent readback, and matching AdminApi/WebUI era routing. This establishes the read path without complex mutation semantics.
- **Phase 4: Normal playresult persistence.** Add White normal playresult classification, normal score/crown/play datum writes, favorites/recent side effects if proven, and no-cross-mode/no-cross-era persistence guards. Add Dani writes only when White payloads and catalog data prove the contract.
- **Phase 5: Reward/present and challenge semantics.** Integrate Donpoint/present/reward progression only after White field placement and `present.xml` semantics are understood. Investigate embedded challenge arrays separately; keep ChallengeCompe/AdminApi Don Challenge disabled until White-specific progress and readback semantics are proven.
- **Phase 6: AdminApi/WebUI closeout and verification.** Extend remaining generic pages, config reporting, favorite limits, customization catalogs, and operational docs. Run targeted handler/persistence/API tests plus cabinet/RPCS3 acceptance for route and payload compatibility.

## Architecture Risks
- **Route evidence gap:** The local White IDB is unusable, and proto files do not prove URL paths. Mitigation: make route ownership an explicit first phase deliverable using logs, captures, or a valid binary; keep Host config disabled until route proof exists.
- **Incorrect AC15 limits:** Reusing Blue/Yellow/Red byte widths can silently corrupt unlock flags, crowns, favorites, or Dan fields. Mitigation: create `Ac15EraProfiles.White` with verified White limits and inspect generated wire plus real payload sizes before enabling persistence.
- **Feature cloning:** Red and Yellow have tempting nearby behavior, but White may lack item shop, Banacoin, Tokkun, battle, gacha, or standalone ChallengeCompe. Mitigation: each feature switch in `Ac15FeatureSet.White` should be evidence-backed and default false when absent.
- **Mapperly drift:** Mapper declarations can look correct while generated code handles nulls, ignored members, or constants unexpectedly. Mitigation: follow current Mapperly docs and inspect emitted generated source for White mappers during verification.
- **Business logic in mappers/controllers:** White-specific reward, classification, and mode rules could leak into adapter mapping. Mitigation: mappers should only translate/classify payload shape; persistence and rule decisions belong in Application handlers/services.
- **Catalog sidecar holes:** Missing server-authored White JSON can make source builds work but published Host output incomplete. Mitigation: add explicit White sidecars and Host copy rules as part of the catalog phase, including empty files where absence is meaningful.
- **Cross-era persistence:** Generic AC15 helpers can be wired to the wrong DbSet or catalog if switch cases are copied carelessly. Mitigation: add White typed accessors, White DbContext partials, and observable no-cross-era tests around normal writes and AdminApi reads.
- **Challenge overreach:** White challenge fields in protobuf may not mean Red-style ChallengeCompe behavior. Mitigation: do not expose Don Challenge UI/API or progress tables until White request/response placement, sidecar data, and readback behavior are proven.
