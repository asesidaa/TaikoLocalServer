## Runtime Rule

Rows with `STILL_MISSING_*`, `NEEDS_USER_APPROVAL`, `DEFER_RUNTIME_USE`, or `DEFER_*` must not be used to emit battle protocol values, advertise battle availability, derive rewards, mutate progression, or mirror normal Blue unlocks.

Initialdata exception: rows 1, 3, 4, 5, 6, and 25 have named user approval from 2026-05-31 for data-derived Blue battle initialdata. The allowed behavior is exact and bounded: parse the required five-file Blue battle XML set through the Blue battle catalog, set `is_battleplay=true` only when that set exists and parses, emit all parsed battle stage IDs into the 8-byte initial stage bitset, emit all parsed battle special move (`必殺技`) reward IDs into the 16-byte initial special bitset, derive `battle_bonds_lv_cap` from `battlenpcinfo.xml` `requred_exp` entry count, and emit explicit false/zero defaults when the set is unavailable. The handler/mapper must not hardcode the current IDs, byte values, or cap.

`PROVEN` rows are narrow. Rows 7-16 permit only the exact battleuserdata response parser/default behavior described above; they do not approve menu timing, initialdata mirroring, token rewards, stage graph behavior, stage `33`, boss-life completion, or normal unlock mirrors. Row 17 permits battle request classification and normal-state bypass, not progression or reward effects.

Rows 18-24 and 26 are also narrow. The approved behavior is a store/echo boundary for client-reported battle-owned state: typed battle playresult values, release bitset diffs, token balances, assignment, boss-life, and last-stage state may be persisted and returned through battleuserdata where the protocol shape defines the matching response field. The server must not calculate battle rewards, token thresholds, NPC progression, boss completion, stage graph transitions, stage `33` behavior, or normal Blue unlock mirrors from these rows.

## Approval Sources

Rows 1, 3, 4, 5, 6, and 25 have named user approval from the 2026-05-31 latest user decision for data-derived Blue battle initialdata. The approval is exact: unlock all parsed local battle stages and battle special move (`必殺技`) reward IDs, derive the bonds cap from parsed NPC progression data, and emit concrete defaults when the required local data set is unavailable.
