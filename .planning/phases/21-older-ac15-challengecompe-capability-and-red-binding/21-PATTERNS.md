# Phase 21: Older-AC15 ChallengeCompe Capability and Red Binding - Pattern Map

**Mapped:** 2026-06-14
**Scope:** Red ChallengeCompe evidence, catalog, persistence, playresult mutation, reward lock/grant, and readback.

## Target Pattern

1. Keep ChallengeCompe behavior shared and transport-agnostic in application/catalog code.
2. Keep Red-owned route, generated wire DTOs, persistence tables, and sidecar data.
3. Treat public DonChare pages as product scope only.
4. Persist only Red-owned raw facts and derived progress from eligible non-Tokkun playresults.
5. Read back active progress through Red `challengecompe.php` only where Red evidence proves the route/response surface.

## Shared Patterns To Reuse

### Era-Owned Catalog Sidecars

Use the Red catalog loader shape:

- JSON lives under `Host/wwwroot/data/red`.
- Runtime paths resolve through `PathHelper.GetDataPath(GameEra.Red)`.
- Era catalog interface exposes typed data to handlers.
- Server-authored JSON should be copied in build/publish output even when intentionally empty.

Do not hardcode `wwwroot/data/red` in handlers.

### AC15 Locked Song Readback

Use the existing `Ac15UserDataService` lock pattern:

- Build release flags from catalog release songs plus save release flags.
- Clear lock bits from a `LockedSongIds` collection.
- Keep challenge reward-song locks as input to the Red userdata snapshot.

Do not write a separate userdata wire mutation path for locks.

### Red Playresult Handler

Keep the existing order:

1. Reject invalid BAID / missing user.
2. Classify Tokkun before normal/Dani/ChallengeCompe.
3. Return from Tokkun after tutorial-only mutation.
4. Use validated non-Tokkun stage facts for normal/Dani and ChallengeCompe.

ChallengeCompe mutation must not run on Tokkun and must not write normal score/crown/Dani/profile/favorite/recent state.

### Red Persistence

Use the current Red partial DbContext pattern:

- Entities live under `Domain/Entities`.
- DbSets are exposed in `ITaikoDbContext.Red.cs`.
- EF mapping lives in `TaikoDbContext.Red.cs`.
- Migration is generated through `dotnet ef migrations add <Name> --project Infrastructure --startup-project Host`.

Do not add shared gameplay tables for ChallengeCompe.

### Mapperly Boundary

The Red ChallengeCompe mapper should follow the Yellow ChallengeCompe mapper shape: Mapperly projections and mechanical conversions only. If Mapperly warnings show DTO boundary problems, narrow the application DTO instead of writing aggregate mapper bodies.

## Anti-Patterns

| Anti-Pattern | Why It Is Rejected |
|--------------|--------------------|
| Red-only shared capability type names | ChallengeCompe is older-AC15 shared behavior with Red as first binding. |
| Shared ChallengeCompe gameplay tables | Era state must stay separate; Phase 21 writes Red-owned state only. |
| Public wiki/blog fields as schema | Product scope is not endpoint/schema authority. |
| Auto-enrolling every Red user | Enrollment is `UserSaveDataRed.IsChallengeCompe`. |
| `challengecompe.php` mutates opt-in | Readback must not enroll users. |
| Filling `ary_user_compe_stat` or `ary_bng_compe_stat` | User/BNG buckets are separate evidence-gated features. |
| Tokkun progress/reward writes | Tokkun playresults are excluded. |
| Rewardcard/rewardexecution involvement | D-22 keeps them simple compatibility for this phase. |
| Source-text tests | Repo test policy requires observable behavior, not implementation-shape assertions. |

## Recommended Plan Split

### Plan 01 - Evidence And Catalog Contract

Create the evidence artifact, shared catalog model, Red catalog sidecar, Red catalog loader access, and publish-copy entries. Include the explicit checkpoint: if local evidence beyond empty success is insufficient, record the gap before executing stateful plans.

### Plan 02 - Red Persistence And Progress Service

Add Red-owned raw fact/progress tables and a shared ChallengeCompe evaluator that consumes active catalog tasks plus `ary_challenge_id` facts. Persist raw facts and derived progress only for eligible enrolled non-Tokkun Red uploads.

### Plan 03 - Reward Grants And Userdata Locks

Apply configured reward locks and immediate reward grants through Red release-song/title flags. Integrate locked reward songs into Red userdata readback.

### Plan 04 - Red Readback Route

Bind Red `challengecompe.php` to Mediator, map Red request/response, return active progress in `ary_challenge_stat`, and keep user/bng stats empty. Ensure readback does not mutate opt-in.

### Plan 05 - Verification And Closeout

Run focused and regression verification, update evidence/verification artifacts, and record any remaining stateful gaps before Phase 22.
