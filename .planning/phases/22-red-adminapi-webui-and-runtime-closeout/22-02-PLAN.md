# Plan 22-02 - Don Challenge AdminApi And No-Opt-In Boundary

<objective>
Provide a dedicated Red Don Challenge AdminApi read model for the WebUI and align ChallengeCompe runtime behavior with the Phase 22 decision that Don Challenge has no opt-in gate. Covers D-07, D-09, D-10, D-12, D-13, D-14, and D-15.
</objective>

## Must Haves

- `UserSaveDataRed.IsChallengeCompe` must not gate Red Don Challenge row creation, reward locks, reward grants, or AdminApi/WebUI availability.
- The AdminApi read model exposes active configured personal tasks, user progress, and reward status only.
- Raw uploaded facts, user-created competition buckets, BNG/global buckets, cabinet compatibility diagnostics, and opt-in state are not exposed.
- Existing cabinet `challengecompe.php` remains separate from the Don Challenge AdminApi contract.

## Decision Coverage

- D-07: Don Challenge uses a dedicated AdminApi surface, not `UserSettings`.
- D-09: raw uploaded ChallengeCompe facts are not exposed.
- D-10: reward status reports earned, locked, or unavailable.
- D-12: Don Challenge has no opt-in gate.
- D-13: progress mutation, readback, reward locks, and reward grants are not gated by `IsChallengeCompe`.
- D-14: no opt-in toggle or editable opt-in field is added.
- D-15: tests cover Don Challenge API data, reward status, and no-cross-era/no-cross-mode behavior.

<threat_model>

- Risk: the AdminApi could leak raw uploaded facts or wire bucket names. Mitigation: build contracts from catalog tasks, progress rows, and reward status only.
- Risk: the old opt-in flag could silently gate progress or locks. Mitigation: tests use `IsChallengeCompe = false` and require progress/locks.

- Risk: reward status could imply wallet/shop authority. Mitigation: status is derived only from configured ChallengeCompe rewards and Red save flags.
</threat_model>
