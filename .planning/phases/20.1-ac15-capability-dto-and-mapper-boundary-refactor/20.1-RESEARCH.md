### Locked Decisions

## Implementation Decisions

### Response Shape
- **D-01:** Use semantic response sections, not one flat `Ac15BaidResponse` or `Ac15UserDataResponse` bucket with every possible field.
- **D-02:** Model AC15 responses as a shared older-AC15 spine plus small behavior/generation variant sections. The proto evidence shows a shared BAID/userdata core with variations around shop medals, reward/Don points, Tokkun, WaiWai, explain/devil flags, ChallengeCompe, and tutorial fields.
- **D-03:** Section/profile names must describe behavior and field groups, not era identity. A profile currently used by one era is allowed only when it represents a real capability/generation combination, not `BlueResponse`, `RedResponse`, etc.
- **D-04:** Do not represent unsupported behavior with null/default fields inside a broad response bucket. Unsupported behavior should be absent from the selected section/profile shape.
- **D-05:** BAID new-user/no-save handling uses the existing simple path: the handler indicates new-user state to the controller by a suitable method, and the controller returns the simple wire response without the section mapper path.

### Aggregation And Assembly
- **D-06:** Handlers decide semantic section availability because handlers know the loaded runtime facts and supported behavior. Their output stops at application-level section/profile results; they must not assemble wire DTOs or mapper-shaped field packets.
- **D-07:** Controllers/adapters are the owners of final wire assembly because adapting application results to generated wire shapes is adapter responsibility. No other layer should produce the final wire response object for these endpoints.
- **D-08:** Controller assembly should be simple: instantiate the generated wire response, then call Mapperly-generated existing-target section apply methods for the section types configured for that controller/wire shape.
- **D-09:** Some composition step is unavoidable. Generated Mapperly derived-type/interface dispatch is allowed at controller level when configured with the expected section types. Handwritten `foreach`/`switch` capability aggregation remains forbidden.

### Mapper Boundary
- **D-10:** Mapper classes contain Mapperly declarations and mechanical helper conversions only. They must not contain handwritten aggregate `Map` methods that compose BAID/userdata responses.
- **D-11:** Allowed mapper helpers are mechanical only: property renames, byte normalization, protocol constants, null/default protocol conversions, and generated existing-target or derived-type mapping configuration.
- **D-12:** Mapper classes must not decide support, presence, business policy, persistence behavior, response composition, or capability ordering.
- **D-13:** Optional protocol absence must rely on nullable generated wire fields and Mapperly null handling. Required protocol fields remain required and must not be nullable in section contracts.
- **D-14:** Generated-source inspection is required. Build with `EmitCompilerGeneratedFiles=true` and inspect emitted Mapperly `.g.cs` to prove BAID/userdata response mappers are generated section apply mappings and preserve null/absence instead of writing defaults.

### Playresult Audit
- **D-15:** Do not change playresult in this phase. Playresult is input mapping, not response assembly, and its envelope design was approved separately. Record only whether it contains actual business aggregation; do not optimize it as part of 20.1 unless new evidence changes the scope.

### Rejected Designs
- **D-16:** Reject nullable all-capability response aggregates.
- **D-17:** Reject capability lists consumed by mapper-side `foreach`/`switch`.
- **D-18:** Reject moving the same capability dispatch switch from mappers into handlers.
- **D-19:** Reject per-era application response DTO families.
- **D-20:** Reject final semantic endpoint DTOs that are effectively the original `CommonBaidResponse` / `CommonUserDataResponse` shape with a new name.
- **D-21:** Reject handler code that constructs mapper-shaped packets mirroring wire placement sections.

### the agent's Discretion
- The planner may choose exact section, interface, and profile type names.
- The planner may decide whether BAID and userdata are implemented in one plan or split into checkpoint plans, provided the resulting code is simpler and the same boundary rules apply to both.
- The planner may prototype Mapperly nullable existing-target and derived-type behavior during planning or implementation, but the accepted plan must include generated-source verification.

### Deferred Ideas (OUT OF SCOPE)

## Deferred Ideas

- Playresult mapper optimization is deferred. It is input mapping and not part of this response-boundary refactor.

## Summary

Phase 20.1 needs a corrected plan because the current in-progress code replaced broad `Common*` DTOs with capability lists but left aggregation in the wrong place: BAID/userdata handlers build mapper-shaped capability packets, adapter mappers perform `foreach`/`switch` dispatch, and controllers mostly delegate final assembly to mapper `Map` methods. [VERIFIED: codebase grep] This does not satisfy the corrected boundary, because controllers/adapters must own final wire assembly and mappers must only expose generated existing-target apply declarations plus mechanical helper conversions. [VERIFIED: phase context]

The correct redesign is a typed semantic section/profile result from Application, assembled into generated wire objects by each controller. [VERIFIED: phase context] Handlers should return required semantic sections plus optional behavior sections based on loaded facts; controllers should instantiate `BAIDResponse` or `UserDataResponse`, set adapter/request constants, and call Mapperly-generated `Apply(section, [MappingTarget] response)` methods for the sections that are part of that controller's wire shape. [CITED: https://mapperly.riok.app/docs/configuration/existing-target/] Mapperly derived-type/interface mapping is acceptable only when the dispatch is generated and invoked at the controller boundary for a known profile variant; an `IEnumerable<ISection>` plus loop repeats the rejected design. [CITED: https://mapperly.riok.app/docs/configuration/derived-type-mapping/] [VERIFIED: phase context]

**Primary recommendation:** Plan a direct controller-assembly rewrite: replace capability lists with typed existing-user profiles/sections, delete mapper aggregate `Map` methods, keep BAID new-user/no-save responses on the existing simple controller branch, and verify with focused behavior tests plus emitted Mapperly generated-source inspection. [VERIFIED: phase context + codebase grep]

## Common Pitfalls

### Pitfall 1: Treating "No Mapper Switch" As Enough

**What goes wrong:** The switch moves from mapper to handler or a helper, but the architecture still has capability-list dispatch. [VERIFIED: rejected plan docs]

**How to avoid:** Do not return `IReadOnlyList<ISection>` or a list-like capability container. Use typed profile properties and direct controller apply calls. [VERIFIED: phase context]

### Pitfall 2: Replacing Capability Lists With a Flat DTO

**What goes wrong:** A final `Ac15UserDataResponse` contains every possible wire field and a mapper projects it directly to each era. [VERIFIED: rejected plan docs]

**How to avoid:** Keep required shared spine sections and behavior-named optional sections; reject any DTO that is effectively `CommonUserDataResponse` with a new namespace. [VERIFIED: phase context]

### Pitfall 3: Letting Handlers Know Wire Placement

**What goes wrong:** Handlers build records whose only purpose is to mirror BAID/userdata wire fields. [VERIFIED: codebase grep]

**How to avoid:** Handler records should be explainable as semantic readback facts: identity, avatar, customization inventory, Dan status, song availability, mode flags, tutorial state, reward progress. [VERIFIED: phase context]

### Pitfall 4: Accidental Optional Field Defaulting

**What goes wrong:** Unsupported sections are represented with zero/false defaults, causing generated protobuf `ShouldSerialize*` to emit fields that should be absent. [VERIFIED: codebase grep]

**How to avoid:** Use nullable optional sections and either do not call `Apply` for null sections or configure Mapperly null handling and inspect generated code. [CITED: https://mapperly.riok.app/docs/configuration/mapper/#null-values]

### Pitfall 5: Tests That Enforce Source Shape Instead Of Behavior

**What goes wrong:** Verification uses source-text assertions for controller names, mapper attributes, or generated wire property existence. [VERIFIED: AGENTS.md]

**How to avoid:** Keep automated tests focused on observable wire serialization, handler readback facts, no-cross-era state, protocol presence/absence, and fixed-width byte packing. [VERIFIED: AGENTS.md]
