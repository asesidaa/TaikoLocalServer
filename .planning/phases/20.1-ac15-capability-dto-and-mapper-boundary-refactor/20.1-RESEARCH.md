# Phase 20.1 - Research Notes

## Scope Confirmation

Phase 20.1 should refactor the confirmed dirty AC15 response DTO families, not every response mapper in the game protocol adapters. The playresult refactor already introduced an AC15-specific capability input envelope in `Application/Dtos/Ac15/Ac15PlayResultInput.cs`; BAID and userdata still return broad `Common*` DTOs that force mappers and handler partials to carry era-shaped or behavior-shaped decisions in the wrong layer.

The implementation target is:

- AC15 BAID responses use an AC15-specific capability response boundary.
- AC15 userdata responses use an AC15-specific capability response boundary.
- Nijiiro can keep the existing `CommonBaidResponse` and `CommonUserDataResponse` path unless execution discovers an unrelated cleanup need.
- Mapperly attributes may rename capability/application member names to generated wire names. Wire naming is not owned by this repo.
- Mappers remain mechanical projection only: field placement, byte normalization, null-to-default presence, constants, and collection conversion are acceptable; mode, era, no-write, persistence, and unsupported-capability decisions are not.

## BAID Findings

Current BAID flow:

- `Application/Handlers/BaidQuery.cs` returns `CommonBaidResponse` for Nijiiro, Green, Blue, Yellow, and Red.
- `Application/Handlers/BaidQuery.Blue.cs`, `.Green.cs`, `.Yellow.cs`, and `.Red.cs` all build the same broad response object with shared identity plus AC15 profile/customization/Dan/shop/reward facts.
- `Application/Dtos/CommonBaidResponse.cs` owns the base identity fields.
- `Application/Dtos/CommonBaidResponse.Green.cs` adds AC15 customization, shop medal, Dan, tone, person, WaiWai, and favorite-costume fields.
- `Application/Dtos/CommonBaidResponse.Red.cs` adds `RewardPtn`.
- `Application/Dtos/CommonBaidResponse.Nijiiro.cs` adds Nijiiro-specific profile/readback fields.
- AC15 `BaidResponseMapper.cs` files map the same broad DTO differently per era. Red has both current and V08R00 wire response placement.

Observed issue:

- `CommonBaidResponse` is no longer a true common application shape. It mixes Nijiiro profile data, AC15 identity, AC15 customization readback, shop medals, Dan flags, WaiWai tutorial, and Red reward compatibility.
- The Green partial file is effectively the AC15 BAID extension point, so Blue, Yellow, and Red depend on Green-named DTO placement.
- Red currently sets `IsAutoCostumeOn` in the handler, but the current Red wire does not map that field. That is the useful warning: the DTO is wide enough to carry unsupported facts and lets mappers silently decide what to ignore.

Recommended shape:

- Add an AC15-specific BAID query/response boundary, for example `Ac15BaidQuery : IRequest<Ac15BaidResponse>`.
- Add `Application/Dtos/Ac15/Ac15BaidResponse.cs` with capability records rather than era records:
  - `Ac15BaidIdentity` for result/new-user/baid/name/language.
  - `Ac15BaidProfileReadback` for title, title plate, colors, costume slots, default tone, last-play datetime.
  - `Ac15BaidCostumeFlags` for five costume flag arrays.
  - `Ac15BaidShopMedalReadback` for Don/Katsu medals and item-shop tutorial when the era owns shop medals.
  - `Ac15BaidDanReadback` for display-Dan, got-Dan flags, got-Dan max, and extra-Dan flags.
  - `Ac15BaidCompatibilityReadback` for WaiWai tutorial, person id, reward pattern, and any proven older-AC15 compatibility fact.
- Unsupported capability segments should be `null` or absent, not default-filled records.
- Controllers for Blue, Green, Yellow, and Red should call the AC15 query and map `Ac15BaidResponse` to wire. Nijiiro controllers stay on `BaidQuery` and `CommonBaidResponse`.

## Userdata Findings

Current userdata flow:

- `Application/Handlers/UserDataQuery.cs` returns `CommonUserDataResponse` for Nijiiro, Green, Blue, Yellow, and Red.
- `Application/Ac15/Ac15UserDataService.BuildResponse` returns `CommonUserDataResponse`.
- Blue, Green, Yellow, and Red handler partials call the shared service, then patch era-specific fields into the same response:
  - Blue: `IsDevilBlue`.
  - Green: `IsDevilGreen`.
  - Yellow: `IsDevilYellow`, `IsExplainYellow`.
  - Red: `IsDevilRed`, `IsExplainRed`, `TotalGetDonpoint`, `TotalUseDonpoint`, `RewardProgress`, `DifficultyTutorialFlg`.
- `Application/Dtos/CommonUserDataResponse.Nijiiro.cs` contains fields that are now also used by AC15 service output, so the naming and ownership are misleading.
- `Application/Dtos/CommonUserDataResponse.Blue.cs`, `.Green.cs`, `.Yellow.cs`, and `.Red.cs` contain era-named fields that all represent behavior/capability facts.

Observed issue:

- `CommonUserDataResponse` has become an AC15 plus Nijiiro union. Era-suffixed fields exist only so mappers can put the same behavior into different generated wire names.
- `Ac15UserDataService` produces a DTO owned outside `Application/Ac15`, then era handlers mutate it after the shared service returns. This makes response composition harder to reason about and makes mappers compensate for missing capability structure.

Recommended shape:

- Add an AC15-specific userdata query/response boundary, for example `Ac15UserDataQuery : IRequest<Ac15UserDataResponse>`.
- Move AC15 userdata service output to an AC15 response record, for example `Application/Dtos/Ac15/Ac15UserDataResponse.cs`.
- Use capability records:
  - `Ac15UserDataSongReadback` for song hash, release bitsets, tone/title flags, favorite/recent, and recommendations.
  - `Ac15UserDataProfileCounters` for genre and profile counters.
  - `Ac15UserDataDisplaySettings` for Dan display, level display, Tojiru, Devil, Explain, and Shin where supported.
  - `Ac15UserDataOptionSettings` for option/default-option settings and preference fields.
  - `Ac15UserDataTutorialReadback` for Tokkun, item-shop, difficulty, or other proven tutorial flags that belong in userdata readback.
  - `Ac15UserDataRewardReadback` for Red Don point and reward progress facts.
- Keep `IsDevil` and `IsExplain` as canonical capability names. Do not create new `IsDevilBlue`, `IsDevilGreen`, `IsDevilYellow`, `IsDevilRed`, `IsExplainYellow`, or `IsExplainRed` members.
- Keep unsupported capability records null. Do not make mappers infer support from era or mode.

## Nearby DTO And Mapper Audit

Initial audit target:

- `Application/Dtos/CommonInitialDataCheckResponse*.cs`
- `Application/Handlers/GetInitialDataQuery*.cs`
- `Adapters.GameProtocol.*/Mappers/InitialDataMappers.cs`

Current read:

- Initialdata is closer to the desired state than BAID/userdata. The shared service produces mostly common startup fields plus explicit Blue battle and Green/older-AC15 list placement fields.
- Some list names are era-labeled (`AryGreenTelopDatas`, `AryYellowTelopDatas`, etc.), but the current mapper behavior is mostly adapter-local wire placement and does not appear to require mode/era/business decisions in mapper code.
- This phase should audit and document initialdata, self-best, item-shop, folder/telop/recommend/Taikojuku, and ChallengeCompe surfaces, but should only refactor newly discovered hotspots when they have the same issue as BAID/userdata.

Do not refactor solely because:

- A Mapperly `[MapProperty]` rename is needed.
- Generated wire uses awkward names.
- A mapper has a mechanical helper for fixed byte widths, nullable presence, or list conversion.

Refactor if:

- A DTO carries unsupported capabilities that mappers silently ignore.
- A mapper determines mode, era, no-write behavior, persistence semantics, or capability support.
- A supposedly common DTO has era-suffixed application fields standing in for behavior/capability facts.

## Validation Architecture

Useful existing coverage:

- `Tests/Blue/BlueMapperTests.cs` covers Blue userdata Tokkun field presence/absence, display-Dan fallback, and BAID fixed-width costume defaults.
- `Tests/Green/GreenUserDataMapperTests.cs` covers Green display-Dan sentinel behavior and nullable field placement.
- `Tests/Yellow/YellowCompatibilityResponseShapeTests.cs` compares Blue and Yellow BAID/userdata serialized shape where compatibility depends on field placement.
- `Tests/Red/RedProtocolMapperTests.cs` covers Red BAID field numbers, V08R00 BAID placement, and Red userdata Don point fields.
- `Tests/{Blue,Green,Yellow,Red}/*IdentityHandlerTests.cs` cover BAID/userdata handler readback against era-owned state.
- `Tests/Ac15/Ac15UserDataServiceTests.cs` covers shared userdata service behavior.

Test strategy:

- Update existing tests to instantiate the new AC15 response records and queries.
- Preserve meaningful wire field placement and presence tests.
- Add no copy-only mapper tests.
- Keep handler tests focused on observable response facts and era-owned state boundaries.
- Use build/source-generation as the Mapperly proof.
