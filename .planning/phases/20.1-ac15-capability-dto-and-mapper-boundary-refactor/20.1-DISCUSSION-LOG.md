## Response Shape

| Option | Description | Selected |
|--------|-------------|----------|
| Section contracts | Use named semantic section records as the Application output, not one flat all-era response bucket. | Yes |

**User's choice:** Section contracts.
**Notes:** User asked for an example and rejected any design that becomes the original `CommonResponse` shape with a new name.

| Option | Description | Selected |
|--------|-------------|----------|

**User's choice:** Capability names.
**Notes:** The user clarified that responses are very similar across generations but have many capability-level variations. Older generations are expected to be closer to Red while most fields remain similar.

| Option | Description | Selected |

**Notes:** Proto scans of Green, Blue, Yellow, and Red BAID/userdata shapes support a shared spine plus variation clusters.

| Option | Description | Selected |

**Notes:** New-user/no-save BAID has nothing to load and should bypass the complex mapper path.

## Aggregation Owner

| Option | Description | Selected |
|--------|-------------|----------|
| Application composer | Handlers load facts, then call a named Application composer that returns the section/profile response. | |
| Handler-owned | Handlers assemble final section/profile responses directly, with strict rules against mapper-shaped packets. | |
| Service-owned | Expand existing services like Ac15UserDataService so they load and compose more of the response. | |
| User correction | Controllers own final wire assembly. Handlers return semantic sections; controllers create the wire response and call Mapperly existing-target section apply methods. | Yes |

**User's choice:** Controllers own final wire assembly, and final mapping is simple section-to-target apply calls.
**Notes:** The user linked Mapperly existing-target documentation. Handler output stops at application-level section/profile results.

| Option | Description | Selected |
|--------|-------------|----------|
| Non-mapper assembler | A named composer/assembler calls generated existing-target section mappers; mapper classes only contain generated Apply methods. | |
| Controller | Controller creates the wire response and calls section mappers directly after Mediator returns sections. | Yes |
| Handler | Handler decides sections and returns something already arranged so the adapter only performs mechanical apply calls. | |

**User's choice:** Controller-owned final assembly.
**Notes:** The user clarified that each handler already knows which sections it needs, but should not do mapper-like work or produce the final wire response.

| Option | Description | Selected |
|--------|-------------|----------|
| Typed section set | Shared code returns named section records or a profile record; era handlers add/remove sections by choosing the profile. | |
| Raw facts only | Shared code returns raw domain facts and each era handler creates all section records itself. | |
| Final profile | Shared code returns the full response profile for common generations, and era handlers only add rare extras. | |
| User correction | Controllers adapt handler results to wire shape because adapters are for adaptation. | Yes |

**User's choice:** Controllers own final wire assembly.
**Notes:** Handlers know what semantic sections to return; controllers know the wire shape.

| Option | Description | Selected |
|--------|-------------|----------|
| Typed container | Handlers return a typed section container with named required/optional accessors; controllers call only the sections their wire shape supports. | |
| Section list | Handlers return a list of section records; controllers iterate/filter by section type before applying Mapperly methods. | |
| Profile records | Handlers return one of several capability-profile records; controllers have one direct assembly method per profile. | |
| User idea | Consider interfaces and Mapperly derived-type mapping. | Yes |

**User's choice:** Consider interface/derived-type mapping.
**Notes:** The agent checked Mapperly derived-type docs and noted that generated dispatch uses a switch internally.

| Option | Description | Selected |
|--------|-------------|----------|
| No dispatch | Do not use derived-type section dispatch; use direct calls for known section/profile types. | |
| Generated only | Allow Mapperly-generated derived-type dispatch, but no handwritten switch/foreach in mapper code. | Yes |
| Prototype first | Test Mapperly generated source on a small response shape before deciding. | |

**User's choice:** Generated only.
**Notes:** Generated derived-type dispatch is allowed at controller level because the controller configures expected types and no handwritten switch is used.

## Mapper Limits

| Option | Description | Selected |
|--------|-------------|----------|
| Yes | Controller owns final assembly; mapper classes expose only generated apply methods and mechanical helper conversions. | Yes |
| Refine | Keep this direction but discuss exact allowed/disallowed mapper code first. | |
| No | Do not lock this mapper rule yet. | |

**User's choice:** Yes.
**Notes:** The user corrected the wording: controllers control final assembly.

| Option | Description | Selected |
|--------|-------------|----------|
| Mechanical only | Allow byte normalization, constants, property renames, null/default protocol conversions, and generated derived apply. | Yes |
| No helpers | Only generated declarations; move every helper/default into controller or Application sections. | |
| Broad helpers | Allow simple helper predicates and section presence helpers if they do not touch persistence. | |

**User's choice:** Mechanical only.
**Notes:** Mapper classes must not make support, presence, aggregation, or business decisions.

| Option | Description | Selected |
|--------|-------------|----------|
| Inspect Mapperly output | Build with generated files and verify response mappers contain generated apply methods, not handwritten aggregation. | Yes |
| Compile only | Rely on build/tests and the code review of handwritten mapper files. | |
| Strict audit list | Require an explicit checklist for every BAID/userdata mapper across Green/Blue/Yellow/Red. | |

**User's choice:** Inspect Mapperly output.
**Notes:** Generated-source inspection is an acceptance gate.

| Option | Description | Selected |
|--------|-------------|----------|
| Yes | Use nullable section/source properties and Mapperly null behavior; verify generated code and wire nullability. | Yes |
| Explicit calls | Controllers only call apply methods for non-null sections, avoiding null-source mapper reliance. | |
| Decide in plan | Record the requirement, then prototype exact Mapperly null-source behavior during planning. | |

**User's choice:** Yes.
**Notes:** The user clarified that if a section is optional and not present, it is null and Mapperly should map it to null. Required sections must not be nullable. Generated proto shapes need null enabled so optional fields can preserve absence.
