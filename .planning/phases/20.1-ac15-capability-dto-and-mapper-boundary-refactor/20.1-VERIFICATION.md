# Phase 20.1 Verification

Completed: 2026-06-14
Status: passed

## Boundary Verified

Controllers control final assembly.

- Handlers return behavior-named semantic application sections.
- Controllers instantiate final generated BAID/userdata wire response objects.
- Controllers set route-level response constants.
- Controllers apply returned non-null semantic sections through Mapperly-generated `Apply(section, response)` methods.
- BAID/userdata mappers contain Mapperly declarations plus mechanical conversion helpers only.
- No BAID/userdata mapper owns final response construction, capability iteration, support switches, or response aggregation.

## Rejected Design Audit

| Decision | Rejected design | Final audit |
|----------|-----------------|-------------|
| D-16 | Nullable all-capability response aggregates | No `Capabilities` list or all-capability AC15 userdata/BAID response bucket remains. |
| D-17 | Capability lists consumed by mapper-side `foreach`/`switch` | BAID/userdata mappers have no aggregate `Map`, `foreach`, or support `switch`. |
| D-18 | Moving the capability dispatch switch into handlers | AC15 handlers return semantic response properties and do not build dispatch lists or mapper packets. |
| D-19 | Per-era application response DTO families | No `Blue*Response`, `Green*Response`, `Yellow*Response`, or `Red*Response` application DTO family exists for AC15 BAID/userdata. Wire DTOs remain adapter-owned generated protocol types. |
| D-20 | Renamed `CommonBaidResponse` / `CommonUserDataResponse` endpoint buckets | AC15 BAID/userdata DTOs are behavior-section records. Nijiiro `Common*` DTOs remain unrelated existing surfaces. |
| D-21 | Handler-built mapper-shaped packets mirroring wire placement | AC15 handlers do not construct mapper packets; controllers choose which semantic sections to apply. |
