# Phase 20.1: AC15 Capability DTO and Mapper Boundary Refactor - Context

**Gathered:** 2026-06-14
**Status:** Ready for planning

<domain>
## Phase Boundary

Refactor AC15 BAID and userdata response boundaries so the code has one clear semantic section boundary, controllers own final wire assembly, and Mapperly remains a generated mechanical projection layer. The refactor applies to existing-user BAID and userdata response mapping for Green, Blue, Yellow, and Red.

This phase must simplify the handler, mapper, and aggregation flow. It must not reintroduce a broad `CommonResponse`-style endpoint bucket, a nullable all-capability aggregate, mapper-side capability dispatch, controller bypass through handler-built wire objects, or handler-built mapper packets.

BAID new-user/no-save responses stay on the existing simple controller path. No complex mapper is needed because there is nothing to load.

Playresult is input mapping and is out of implementation scope for this phase. It should be recorded as audited only; do not rewrite playresult mappers now unless a later phase finds true business aggregation there.

</domain>

<decisions>
## Implementation Decisions

### Response Shape
- **D-01:** Use semantic response sections, not one flat `Ac15BaidResponse` or `Ac15UserDataResponse` bucket with every possible field.
- **D-02:** Model AC15 responses as a shared older-AC15 spine plus small behavior/generation variant sections. The proto evidence shows a shared BAID/userdata core with variations around shop medals, reward/Don points, Tokkun, WaiWai, explain/devil flags, ChallengeCompe, and tutorial fields.
- **D-03:** Section/profile names must describe behavior and field groups, not era identity. A profile currently used by one era is allowed only when it represents a real capability/generation combination, not `BlueResponse`, `RedResponse`, etc.
- **D-04:** Do not represent unsupported behavior with null/default fields inside a broad response bucket. Unsupported behavior should be absent from the selected section/profile shape.
- **D-05:** BAID new-user/no-save handling uses the existing simple path: the handler indicates new-user state to the controller by a suitable method, and the controller returns the simple wire response without the section mapper path.

### Aggregation And Assembly
- **D-06:** Handlers decide semantic section availability because handlers know the loaded runtime facts and supported behavior. Their output stops at application-level section/profile results; they must not assemble wire DTOs or mapper-shaped field packets.
- **D-07:** Controllers/adapters are the owners of final wire assembly because adapting application results to generated wire shapes is adapter responsibility. No other layer should produce the final wire response object for these endpoints.
- **D-08:** Controller assembly should be simple: instantiate the generated wire response, then call Mapperly-generated existing-target section apply methods for the section types configured for that controller/wire shape.
- **D-09:** Some composition step is unavoidable. Generated Mapperly derived-type/interface dispatch is allowed at controller level when configured with the expected section types. Handwritten `foreach`/`switch` capability aggregation remains forbidden.

### Mapper Boundary
- **D-10:** Mapper classes contain Mapperly declarations and mechanical helper conversions only. They must not contain handwritten aggregate `Map` methods that compose BAID/userdata responses.
- **D-11:** Allowed mapper helpers are mechanical only: property renames, byte normalization, protocol constants, null/default protocol conversions, and generated existing-target or derived-type mapping configuration.
- **D-12:** Mapper classes must not decide support, presence, business policy, persistence behavior, response composition, or capability ordering.
- **D-13:** Optional protocol absence must rely on nullable generated wire fields and Mapperly null handling. Required protocol fields remain required and must not be nullable in section contracts.
- **D-14:** Generated-source inspection is required. Build with `EmitCompilerGeneratedFiles=true` and inspect emitted Mapperly `.g.cs` to prove BAID/userdata response mappers are generated section apply mappings and preserve null/absence instead of writing defaults.

### Playresult Audit
- **D-15:** Do not change playresult in this phase. Playresult is input mapping, not response assembly, and its envelope design was approved separately. Record only whether it contains actual business aggregation; do not optimize it as part of 20.1 unless new evidence changes the scope.

### Rejected Designs
- **D-16:** Reject nullable all-capability response aggregates.
- **D-17:** Reject capability lists consumed by mapper-side `foreach`/`switch`.
- **D-18:** Reject moving the same capability dispatch switch from mappers into handlers.
- **D-19:** Reject per-era application response DTO families.
- **D-20:** Reject final semantic endpoint DTOs that are effectively the original `CommonBaidResponse` / `CommonUserDataResponse` shape with a new name.
- **D-21:** Reject handler code that constructs mapper-shaped packets mirroring wire placement sections.

### the agent's Discretion
- The planner may choose exact section, interface, and profile type names.
- The planner may decide whether BAID and userdata are implemented in one plan or split into checkpoint plans, provided the resulting code is simpler and the same boundary rules apply to both.
- The planner may prototype Mapperly nullable existing-target and derived-type behavior during planning or implementation, but the accepted plan must include generated-source verification.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `Application/Ac15/Ac15UserDataService.cs` currently computes shared userdata facts. It should be adjusted to return section-shaped semantic data instead of capability-list packets or a broad response bucket.
- `Application/Ac15/*Ac15UserDataAdapter.cs` creates reusable snapshots from save/catalog/favorites/recent/unlock facts and remains a useful handler input boundary.
- `Application/Ac15/Ac15ProtocolBytes.cs`, era `*ProtocolBytes`, and `Ac15EraProfiles` provide byte widths and protocol limits for mechanical section mapping.
- Mapperly existing-target mappings can replace handwritten mapper aggregation by generating `Apply(section, target)` methods.

### Established Patterns
- Controllers deserialize wire DTOs, map/send Mediator requests, and map application responses back to generated wire DTOs.
- Handlers are era workflow roots and may decide which semantic sections exist from loaded rows/catalog facts.
- Adapters own generated wire shapes and final transport assembly.
- Mapperly owns mechanical projection; manual mapper code is limited to explicit mechanical conversions.
- AC15 era state remains separate through direct `ITaikoDbContext` and concrete era `DbSet` selection.

### Integration Points
- `Application/Dtos/Ac15/Ac15BaidResponse.cs` and `Application/Dtos/Ac15/Ac15UserDataResponse.cs`: current rejected capability-list shapes.
- `Application/Handlers/BaidQuery.{Green,Blue,Yellow,Red}.cs`: currently build mapper-shaped capability packets and must be simplified.
- `Application/Handlers/UserDataQuery.{Green,Blue,Yellow,Red}.cs`: currently append capability packets and should instead return section/profile results.
- `Adapters.GameProtocol.{Green,Blue,Yellow,Red}/Mappers/BaidResponseMapper.cs`: currently contain mapper-side `foreach`/`switch` aggregation and must be rewritten.
- `Adapters.GameProtocol.{Green,Blue,Yellow,Red}/Mappers/UserDataMappers.cs`: currently contain mapper-side `foreach`/`switch` aggregation and must be rewritten.
- `Adapters.GameProtocol.{Green,Blue,Yellow,Red}/Controllers/*Baid*` and `*UserData*`: likely final wire assembly owners after the refactor.
- `Tests/Ac15/Ac15CapabilityAssert.cs` and capability-list assertions are tied to the rejected design and should be removed or replaced with behavior/section/wire assertions.

</code_context>

<specifics>
## Specific Ideas

- The response families are very similar across AC15 generations, but with many capability-level variations. Older generations are expected to be closer to Red, while the majority of fields remain similar.
- The design should use base/spine sections plus behavior variants rather than era DTO clones or nullable all-era extras.
- Controllers control final assembly. Handlers return the semantic sections they know from loaded facts; controllers adapt those sections to wire.
- Mapperly derived-type/interface mapping is allowed when generated and configured at the controller/wire boundary. Handwritten switches remain forbidden.
- Generated wire nullability matters. Optional proto fields should stay nullable in generated C# so Mapperly can preserve absence.

</specifics>
