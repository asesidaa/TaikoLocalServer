# Phase 20.1: AC15 Capability DTO and Mapper Boundary Refactor - Context

**Gathered:** 2026-06-13
**Status:** Ready for planning

<domain>
## Phase Boundary

Refactor AC15 application DTO boundaries that still behave like all-era or era-named unions after the playresult capability-input refactor. The phase should make BAID and userdata response DTOs capability-shaped, keep adapter mappers mechanical, and audit nearby AC15 DTOs so clean one-to-one response maps are documented rather than rewritten unnecessarily.

The goal is cleaner behavior/capability DTOs, not a transport rewrite. Generated wire DTOs, routes, proto inputs, and era-owned persistence stay in their current era-owned locations.

</domain>

<decisions>
## Implementation Decisions

### Capability DTO Shape
- **D-01:** Refactor AC15 BAID response data into capability-shaped application records instead of continuing `CommonBaidResponse` as a broad union with era-specific fields.
- **D-02:** Refactor AC15 userdata response data into capability-shaped application records instead of continuing `CommonUserDataResponse` with properties such as `IsDevilBlue`, `IsDevilGreen`, `IsDevilYellow`, `IsDevilRed`, `IsExplainYellow`, and `IsExplainRed`.
- **D-03:** Capability splits should describe behavior and facts: identity/profile basics, customization/costume flags, shop medal/balance facts, Don point/reward compatibility facts, tutorial/readback flags, display flags, challenge flags, and other proven protocol-backed capability groups.
- **D-04:** Per-era application DTOs are not the preferred default. Use per-era types only where capability records cannot cleanly express a real semantic split without hiding an era-only behavior.

### Mapper Boundary
- **D-05:** Mapperly remains strict. Keep `AutoUserMappings = false` and target-required mapping behavior; fix mapper pressure by correcting target shapes rather than weakening diagnostics.
- **D-06:** Mappers may use `[MapProperty]` and related Mapperly attributes to rename application DTO members into generated wire names. Wire naming is not controlled by this repo and should not force poor application-level names.
- **D-07:** Mappers must remain mechanical projection: allowed helper code includes byte normalization, null-to-default conversions required by protocol presence, list/array conversions, constants, and wire placement. Mappers must not decide play mode, era policy, no-write behavior, persistence behavior, or unsupported capability semantics.
- **D-08:** Unsupported capabilities should be absent or omitted, not represented by default-filled records that make mappers or handlers infer behavior that the era does not own.

### Scope And Audit
- **D-09:** Implement the confirmed dirty families first: BAID and userdata. Include a nearby DTO/mapper audit so initialdata and other response mappers are explicitly classified as clean, minor-rename-only, or requiring later work.
- **D-10:** Do not blanket-refactor every AC15 `Common*` DTO in this phase. Initialdata currently looks closer to the desired shape: shared fields plus Blue battle-specific response fields and mostly mechanical Mapperly projection.
- **D-11:** Preserve the playresult capability-input refactor as the model. Do not backslide by creating another all-era union DTO for responses.

### Architecture And Tests
- **D-12:** Keep direct `ITaikoDbContext`, concrete era `DbSet` selection, era-owned persistence, and handler/service orchestration visible. Do not introduce repository-shaped persistence abstractions.
- **D-13:** Keep shared behavior in `Application/Ac15` only where the behavior is value-identical or capability-driven. Era-only protocol facts stay in era partial handlers or adapter-local mappers.
- **D-14:** Tests should protect observable behavior and protocol/readback boundaries: BAID response shape where field placement matters, userdata field placement/presence where cabinet behavior depends on it, and no-cross-era/no-cross-mode persistence if implementation touches state. Do not add one-to-one copy mapper tests.

### the agent's Discretion
- The planner may choose the exact record/type names as long as the result is capability-shaped and avoids era-suffixed application fields for shared facts.
- The planner may decide whether BAID and userdata are implemented in one plan or split into separate plans, but the audit of nearby DTOs should remain in scope.

</decisions>

## Existing Code Insights

### Reusable Assets
- `Application/Ac15/Ac15EraProfiles.cs` and `Application/Ac15/Ac15WirePlacement.cs`: existing profile/wire-placement model for capability-level response decisions.
- `Application/Ac15/Ac15UserDataRecords.cs` and `Application/Ac15/Ac15UserDataService.cs`: current shared userdata snapshot/service path; useful anchor for extracting capability response records.
- `Application/Dtos/Ac15/Ac15PlayResultInput.cs`: current example of capability-shaped AC15 input records after the playresult refactor.

### Established Patterns
- Controllers deserialize wire DTOs, map to application DTOs, send Mediator requests, and map responses back to wire.
- Handler partials remain era orchestration roots and choose concrete era tables/catalogs/profiles.
- `Application/Ac15` owns shared AC15 behavior only after facts are mapped into canonical application shapes.
- Mapperly mappers use `[Mapper]`, `[MapProperty]`, `[MapValue]`, `[MapperIgnoreTarget]`, and small user mappings for mechanical transforms.

### Integration Points
- `Application/Dtos/CommonBaidResponse*.cs`: current BAID response union, including Green/Red/Nijiiro partials and AC15-era fields.
- `Application/Handlers/BaidQuery.*.cs`: Blue, Green, Yellow, and Red build similar `CommonBaidResponse` objects with duplicated customization, Dan, shop, and reward facts.
- `Adapters.GameProtocol.*/Mappers/BaidResponseMapper.cs`: era mappers translate broad application fields into generated BAID wire responses; Red V08R00 has an additional manual mapping path.
- `Application/Dtos/CommonUserDataResponse*.cs`: current userdata response union with era-named fields for `IsDevil*`, `IsExplain*`, Red Don point/reward facts, and Blue Tokkun tutorial.
- `Application/Handlers/UserDataQuery.*.cs`: era handlers currently patch response fields after `Ac15UserDataService.BuildResponse`.
- `Adapters.GameProtocol.*/Mappers/UserDataMappers.cs`: era mappers map era-named application fields back to the same wire fields.
- `Application/Dtos/CommonInitialDataCheckResponse*.cs`, `Application/Handlers/GetInitialDataQuery.*.cs`, and `Adapters.GameProtocol.*/Mappers/InitialDataMappers.cs`: audit target; currently appears mostly clean, with Blue battle fields isolated and mapping mostly mechanical.

</code_context>

<specifics>
## Specific Ideas

- User explicitly accepts attribute-based renaming in mappers because generated wire names are outside this repo's control and application DTO names should be proper.
- User goal: DTOs should split by behavior/capability so mappers do not need business logic such as determining mode or era.
- The playresult capability-input design is the preferred model for this cleanup, but response DTOs should not blindly copy the playresult envelope shape if a smaller response-specific split is cleaner.

</specifics>
