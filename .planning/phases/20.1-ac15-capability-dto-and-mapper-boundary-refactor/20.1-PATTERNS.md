## DTO Boundary Pattern

Use the playresult envelope as the boundary precedent, not as a literal response template:

- AC15-specific top-level type in `Application/Dtos/Ac15`.
- Capability records with canonical behavior names.
- Nullable capability segments when support is optional or era-limited.
- No era-suffixed fields for the same behavior.
- No generated-wire names forced into application-level naming.

For Phase 20.1, this implies:

- `CommonBaidResponse` remains for Nijiiro/base compatibility.
- AC15 BAID uses an `Ac15BaidResponse` family.
- `CommonUserDataResponse` remains for Nijiiro/base compatibility.
- AC15 userdata uses an `Ac15UserDataResponse` family.

## Mapper Pattern

Mappers may:

- Use `[MapProperty]`, `[MapValue]`, `[MapperIgnoreTarget]`, and target-specific helper mappings.
- Rename application members to generated wire names.
- Convert `null` to absent/default wire fields when that is the protocol presence rule.
- Normalize fixed-width byte arrays and collection types.
- Populate constant success/status values that are part of the response contract.

Mappers must not:

- Determine whether a playresult is Tokkun, battle, normal, Dan, ghost, or ChallengeCompe.
- Decide whether an era supports shop medals, Don points, WaiWai, Red reward data, or tutorial flags.
- Read persistence or catalogs.
- Create default-filled records that imply unsupported capability support.

## Persistence And Handler Pattern

Use current AC15 architecture:

- Handlers select concrete era `DbSet`s through direct `ITaikoDbContext` access.
- Shared behavior in `Application/Ac15` accepts canonical facts and era profile data.
- No repository-shaped persistence wrapper should be introduced for this response cleanup.
- Era-owned tables, routes, protos, and generated wire DTOs remain unchanged.

## Test Pattern

Keep and update existing behavior tests:

- Mapper tests only when they protect nontrivial field placement, omission, presence, fixed-width normalization, or compatibility serialization.
- Handler tests for BAID/userdata readback against era-owned state.
- Shared service tests for bitset/counter/display-Dan behavior.
- Build as Mapperly/source-generation proof.

Avoid:

- Source-text tests for mapper attributes, class names, route attributes, or generated wire properties.
- One-to-one copy/echo mapper tests.
- Tests proving `.csproj`, DI registration shape, or source file removal.

## Audit Pattern

For each nearby DTO/mapper family, classify it as one of:

- Clean: capability/common shape is acceptable and mappers are mechanical.
- Rename-only: Mapperly attributes should hide wire naming without changing DTO ownership.
- Refactor later: same union/capability smell exists but is outside BAID/userdata and needs its own phase.
- Refactor now: same issue as BAID/userdata and small enough to fix without broadening Phase 20.1 risk.

Initialdata currently appears "clean" or at most "rename-only"; do not rewrite it unless execution finds mapper business logic or unsupported capability leakage.
