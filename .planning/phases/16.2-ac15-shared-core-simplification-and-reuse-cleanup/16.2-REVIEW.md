## Critical Issues

### CR-01 [BLOCKER]: Green normal play discards compact cabinet timestamps

**File:** `Application/Handlers/UpdatePlayResultCommand.Green.cs:43`
**Issue:** Green still parses `playResultData.PlayDatetime` with plain `DateTime.TryParse`, while AC15 cabinet payloads use compact `yyyyMMddHHmmss`. Blue and Yellow call the shared exact-format parser, and `Ac15NormalPlayService` also uses the shared parser for play/recent rows. Green can therefore persist upload time in `UserSaveDataGreen.LastPlayDatetime` while the rows saved by the shared normal-play service use cabinet play time.
**Fix:** Use `ParseAc15PlayDatetimeOrNow(playResultData.PlayDatetime)` in Green and add a regression asserting Green `LastPlayDatetime` for a compact timestamp.

### CR-02 [BLOCKER]: Green still fails unrecognized AC15 uploads instead of log-skip-success

**File:** `Application/Handlers/UpdatePlayResultCommand.Green.cs:36`
**Issue:** Green combines medal-overflow detection with stage-shape validation and returns `0` for the entire upload when any stage fails `IsValidGreenStage`. Phase decision D-17 requires unrecognized AC15 playresult shapes to be logged for replay, skip unsupported mutation, and return protocol success. Blue and Yellow already return success for medal overflow and filter unsupported normal stages instead of failing the protocol call. This Green branch can make the cabinet see a failed upload and also discards valid stages in a mixed payload.
**Fix:** Split overflow from stage filtering. For overflow, log and return `1` before mutation. For unsupported stages, log each skipped stage, assign `playResultData.AryStageInfoes` to the valid subset, and return `1` without mutation only when no valid Green stages remain.

## Warnings

### WR-01 [WARNING]: Table-only era switches remain scattered through shared services

**File:** `Application/Ac15/Ac15NormalPlayService.cs:87`, `Application/Ac15/Ac15DaniService.cs:90`, `Application/Ac15/Ac15ItemShopService.cs:126`
**Issue:** The shared services still reopen an era switch at many storage operations instead of binding concrete era DbSets and Mapperly delegates once, then running one generic algorithm. Examples include normal-play recent/save/play-row/best/favorite helpers, Dani read/upsert helpers, and item-shop season/purchase/insertion helpers. Direct EF visibility is correct, but this shape keeps table selection interleaved with behavior and makes each shared workflow harder to audit for true policy differences.
**Fix:** Introduce narrow typed binding records local to each AC15 service entry point. Bind concrete DbSets, Mapperly projection delegates, protocol limits, and real policy flags once, then call a generic helper constrained by the existing row-shape interfaces. Do not add repository-shaped persistence adapters.

### WR-02 [WARNING]: Shared normal-play save prelude remains duplicated in era handlers

**File:** `Application/Handlers/UpdatePlayResultCommand.Blue.cs:46`, `Application/Handlers/UpdatePlayResultCommand.Green.cs:35`, `Application/Handlers/UpdatePlayResultCommand.Yellow.cs:48`
**Issue:** Blue, Green, and Yellow still own the same normal-save prelude: medal validation/addition, tutorial flag merges, play-time parsing, area/profile updates, current costume writes, unlock bit writes, profile counters, and Dani save callbacks before calling `Ac15NormalPlayService.SaveAsync`. This is not just cosmetic duplication; it already drifted into CR-01 and CR-02, where Green parses timestamps differently and treats invalid uploads differently. Yellow remains especially noisy even though its unique edges are Tokkun routing, stage filtering, and WaiWai logging.
**Fix:** Move the shared prelude into an AC15 application service that accepts typed save-data accessors, protocol limits, active shop season state, costume/unlock accessors, Dani challenge source, and era hooks. Keep Blue battle/Tokkun, Yellow Tokkun, and Green ghost/AI gates outside that helper.

### WR-03 [WARNING]: Dan score readback bypasses the shared Dani query service

**File:** `Application/Handlers/GetDanScoreQuery.Blue.cs:11`, `Application/Handlers/GetDanScoreQuery.Green.cs:11`, `Application/Handlers/GetDanScoreQuery.Yellow.cs:11`
**Issue:** All three AC15 Dan-score handlers repeat requested-id filtering, Taikojuku challenge lookup, concrete EF query, stage ordering, `ArrivalSongCount` truncation, and response projection. `Ac15DaniService.GetScoresAsync` already centralizes direct EF era binding at `Application/Ac15/Ac15DaniService.cs:78`, but the handlers do not use it.
**Fix:** Route Blue/Green/Yellow handlers through `Ac15DaniService.GetScoresAsync`, then add a shared response projection such as `Ac15DaniMapper.ToCommonDanScoreDataResponse(IReadOnlyList<Ac15DaniScore>)` that owns ordering and stage truncation once.

### WR-04 [WARNING]: Item-shop policy remains split between handlers and a triplicated unlock matrix

**File:** `Application/Handlers/ItemPurchaseCommand.Green.cs:14`, `Application/Handlers/ItemPurchaseCommand.Yellow.cs:16`, `Application/Ac15/Ac15ItemShopService.cs:247`
**Issue:** Blue delegates directly to `Ac15ItemShopService`, but Green handles no-active-season and empty-season cases first, while Yellow handles unsupported requested items with a local season-state query. The shared service then has another era dispatch and three near-identical `Apply*Unlock` switches where only Green song unlocks are a real policy difference. The result is a more complex split than the behavior requires.
**Fix:** Move active-season-missing, empty-season preflight, unsupported-item behavior, and the item-type unlock matrix into `Ac15ItemShopService` behind explicit policy inputs such as `UnlockSongs` plus typed flag accessors. Keep handlers responsible for choosing catalog/save data only.

### WR-05 [WARNING]: Catalog snapshot extraction still manually repeats identical Blue/Green/Yellow mapping

**File:** `Application/Ac15/Ac15CatalogSnapshotFactory.cs:11`
**Issue:** `FromBlue`, `FromGreen`, and `FromYellow` build the same snapshot shape field-by-field. `MapItemShop`, `MapSeason`, and `MapTaikojuku` then repeat identical property copies for Blue, Green, and Yellow catalog records at lines 77, 107, and 161. This is mechanical projection code that Phase 16.2 intended to move into canonical AC15 value shapes or Mapperly-backed projections.
**Fix:** Put the common catalog source shape behind narrow AC15 catalog interfaces/records, or use Mapperly projection overloads plus generic helpers for seasons, item entries, and Taikojuku songs. Keep adapter-local source catalogs, but make the snapshot algorithm one implementation.

### WR-06 [WARNING]: AC15 AdminApi user settings behavior remains triplicated in controllers

**File:** `Adapters.AdminApi/Controllers/UserSettingsController.Blue.cs:19`, `Adapters.AdminApi/Controllers/UserSettingsController.Green.cs:19`, `Adapters.AdminApi/Controllers/UserSettingsController.Yellow.cs:19`
**Issue:** The three AdminApi partials all perform the same business workflow inside controller code: save-data mutation, display-level validation/clamping, costume/title/tone bitset encode/decode, selectable Taikojuku Dan calculation, response assembly, and Dan-score queries. Yellow is still a full third copy with only limits and DbSet selection changed. This violates the repo rule that controllers should map/call application logic, and it leaves shared AC15 WebUI behavior outside `Application/Ac15`.
**Fix:** Extract an `Ac15UserSettingsService` or mediator handler in `Application` that owns the AC15 settings workflow with typed save accessors, protocol limits, and Dan-score DbSet binding. The AdminApi controller partials should only resolve the era route, load/map the request DTO, call the application service, and return the result.

Reviewed the Phase 16.2 source scope at standard depth with special attention to architectural complexity and shared-behavior extraction quality. I found 2 blockers and 6 warnings. The most important pattern is that pure DbSet-selection switches are acceptable only when they are binding edges; several services and handlers still interleave those switches with identical policy or mutation algorithms, which keeps Blue/Green/Yellow behavior harder to reason about than the phase goal allows.

No evidence found that the rejected repository-shaped `IAc15*Persistence` layer returned. Era-owned EF tables remain separate.
