# Review

## Findings

### P1 - Protogen invocation is not captured, so optional value-type generation is inconsistent

There is no tracked source invocation for `.tools/protogen.exe` outside planning/docs/local history, and `.tools/protogen.exe --help` confirms the relevant option is `+nullablevaluetype={yes|no}`. Direct probes show that the same proto generated without that flag exposes optional value fields as non-nullable public properties plus `ShouldSerialize*`; generating with `+nullablevaluetype=yes` changes those public properties to nullable while preserving `ShouldSerialize*` presence.

Current inconsistent examples:

- `Adapters.GameProtocol.White/Wire/Game.cs:1587` exposes optional `difficulty_played_course` as `public uint DifficultyPlayedCourse`.
- `Adapters.GameProtocol.White/Wire/Game.cs:1607` exposes optional `tokkun_tutorial_flg` as `public uint TokkunTutorialFlg`.
- `Adapters.GameProtocol.Murasaki/Wire/Game.cs:1573` exposes optional `reward_ptn` as `public uint RewardPtn`.
- `Adapters.GameProtocol.Kimidori/Wire/Game.cs:1495` exposes optional `reward_ptn` as `public uint RewardPtn`.
- `Adapters.GameProtocol.White/LegacyWire/Game.cs:1501` exposes optional legacy `reward_ptn` as `public uint RewardPtn`.

Probe result: `+nullablevaluetype=yes` changes optional examples such as `RewardPtn`, `SoulGauge`, and `DifficultyPlayedCourse` to `uint?`, while required examples such as `PlayResult` stay `uint`.

Fix plan:

1. Add or update a repo-tracked protocol-generation entrypoint that always passes `+nullablevaluetype=yes` for AC15 wire generation.
2. Regenerate affected generated files instead of manually editing `Wire/` or `LegacyWire/`.
3. Regenerate at least White final, White legacy, Murasaki final, Murasaki legacy, and Kimidori base; audit Kimidori final and newer Momoiro but do not churn them unless output differs.
4. Keep required proto fields non-nullable unless local proto/client evidence proves the schema is wrong.

### P1 - Playresult mappers preserve optional-field presence through ad hoc `ShouldSerialize*` helpers

The mapper helpers are compensating for the inconsistent generated public property types. Once affected wire files are regenerated with nullable value types, several helpers should collapse into direct nullable mappings or shared mechanical conversions.

Examples:

- `Adapters.GameProtocol.White/Mappers/PlayResultMappers.cs:105` maps optional difficulty tutorial through `ShouldSerializeDifficultyTutorialFlg()`.
- `Adapters.GameProtocol.White/Mappers/PlayResultMappers.cs:108` and `:110` split presence/value for difficulty course because the generated public property is non-nullable.
- `Adapters.GameProtocol.White/Mappers/PlayResultMappers.cs:116` maps Tokkun tutorial through `ShouldSerializeTokkunTutorialFlg()`.
- `Adapters.GameProtocol.Murasaki/Mappers/PlayResultMappers.cs:108`, `:111`, `:123`, `:126`, `:129`, and `:132` are `ShouldSerialize*` wrappers around optional reward, boolean, soul-gauge, and hit-count fields.
- `Adapters.GameProtocol.Kimidori/Mappers/PlayResultMappers.cs:109`, `:112`, `:124`, `:127`, `:130`, and `:133` repeat the same pattern.

Fix plan:

1. Regenerate wire first; do not rewrite mappers against stale public types.
2. Replace optional-value `ShouldSerialize*` value helpers with direct nullable mappings where the generated source property is `uint?` or `bool?`.
3. Keep explicit `Has*` mappings only where the Application DTO intentionally stores presence separately, such as `HasDifficultyPlayedCourse`, but derive them from `request.DifficultyPlayedCourse is not null` after regeneration.
4. Keep `ShouldSerialize*` tests where they assert wire serialization presence; the method remains generated for nullable optionals.

### P2 - Some playresult helper cleanup missed legacy/final mapper surfaces

The prior AC15 mapper normalization quick task correctly introduced `Application/Ac15/Ac15MapperNormalization.cs`, but it did not fully cover older compatibility surfaces.

Examples:

- `Adapters.GameProtocol.White/LegacyWire/LegacyMappers.cs:173` still has local `MapUInt`.
- `Adapters.GameProtocol.White/LegacyWire/LegacyMappers.cs:179` still has local `MapBytes`.
- `Adapters.GameProtocol.White/LegacyWire/LegacyMappers.cs:182` still has local `MapString`.
- `Adapters.GameProtocol.White/LegacyWire/LegacyMappers.cs:185` still has local `MapPlayDan`.
- `Adapters.GameProtocol.Kimidori/Mappers/FinalPlayResultMappers.cs:112` and `:115` still use local pass-through helpers for nullable stage facts.

Fix plan:

1. Convert pure legacy/final helpers to `Ac15MapperNormalization` external mappings when they are one-line protocol primitives.
2. Keep era-limit wrappers local where the method binds `Ac15EraProfiles.<Era>.Limits`, matching the previous quick-task decision.
3. Prefer Mapperly direct property mapping for renamed nullable fields when source and target types match after regeneration.

## Non-Issue

Do not make required playresult stage fields nullable just to remove helper friction. The proto files mark these as `required` in several eras:

- White/Red/Yellow/Murasaki/Kimidori/Momoiro `play_result`, `play_score`, `play_dan`, and `stage_mode` are required in the relevant `StageData` messages.
- Blue/Green differ: their `play_result`, `play_score`, `play_dan`, and `stage_mode` fields are optional and already expose nullable public types in current generated wire.

That is an era schema difference, not a Mapperly cleanup target.
